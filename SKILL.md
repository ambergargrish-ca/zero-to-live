# Zero to Live

A workflow for shipping a real website, not a demo: static-first pages, a small API where it earns its place, tests that scale with the size of the change, and deploys you can count.

Preferred stack: Cloudflare Pages (static files plus Pages Functions), D1 (SQLite) and R2 (object storage). Every step works on other hosts; see `references/alternatives.md`.

## The workflow

```
1. Plan  ->  2. Build  ->  3. Check (quick)  ->  4. Secure  ->  5. Verify (full)  ->  6. Deploy (batched)
                 ^________________________________|
```

### 1. Plan
Before writing code, write down: who the site is for, the pages and their single job each, what data is stored and why, which outside services receive data, and what "done" means (Lighthouse targets, browsers, screen sizes). Decide static vs dynamic per page. Read `references/planning.md`.

### 2. Build
- Static-first: pages are plain HTML generated by a build script; only routes that need a database or a secret run server code.
- One shared layout function renders header, footer, privacy link and cookie settings on every page. Never hand-copy a footer.
- No inline scripts or inline event handlers, so the Content Security Policy can forbid them.
- Fingerprint assets (`?v=<hash>`) so browsers never keep stale code.
- Ship SEO and AI-crawler basics from day one: titles, descriptions, canonical URLs, `robots.txt`, `sitemap.xml`, `llms.txt`, JSON-LD.

Read `references/building.md`, then `references/stack-cloudflare.md` for the platform.

### 3. Check (quick tier, every change)
Run only the checks the change can affect. `scripts/quick_check.py` maps changed files to commands through `checks.json`. A copy edit runs the page checks; a server change runs the API suite for that area. Do not run the full suite after every small edit: it is slow, noisy and expensive.

### 4. Secure
Run `scripts/compliance_check.py` on every change. It fails on secrets in the repo, inline scripts, missing security headers and SQL built from request text, and warns when a change touches privacy (new table, column, outside service, cookie or storage key). Work through `references/security.md` for any change to auth, roles, uploads, payments or data access.

### 5. Verify (full tier, before each deploy batch)
Run `scripts/run_suite.py` (all suites, fresh local database per suite, one report) and `scripts/lighthouse.sh` against the local build. Targets: Accessibility 100, Performance 90+ on mobile, Best Practices 95+, SEO 90+ on indexable pages. Read `references/testing.md` and `references/accessibility-performance.md`.

### 6. Deploy (batched)
Every push to the production branch is one build. Collect changes, verify once, deploy once. `scripts/deploy_batch.sh` keeps the count and refuses to deploy a batch that has not passed the full tier. Read `references/deploys.md`, including rollback.

## Key rules

1. **Match test effort to change size.** Quick checks for small edits; the full suite once per deploy batch.
2. **The browser never talks to the database.** Every API route declares who may call it, validates every input, and uses `?` placeholders. Table and column names never come from a request.
3. **Authorize the object, not just the role.** Check that the signed-in user owns or may act on the specific record, every time.
4. **Secrets live in the platform's secret store only.** `.env*`, `.dev.vars*`, `*.pem` and `*.key` are in `.gitignore` from the first commit.
5. **Privacy changes need a human.** A new table, outside service or cookie means the privacy policy is reviewed before deploy.
6. **Consent before tracking.** Analytics and marketing scripts load only after the visitor opts in.
7. **Accessibility is a release gate, not a nice-to-have.** Lighthouse Accessibility below 100 blocks the batch.
8. **Batch deploys and know your budget.** Count builds against the plan limit and say how many are left before deploying.
9. **Every deploy can be undone in one step.** Know the rollback path before you push.
10. **Never ship a debug flag.** Development-only bindings (free checkout, disabled limits, disabled MFA) must be honoured only when a dev-mode flag is set, and that flag must never exist in production.

## Scripts

| Script | Purpose |
|---|---|
| `scripts/quick_check.py` | Run only the checks affected by the current diff |
| `scripts/compliance_check.py` | Secrets, CSP, headers, SQL safety, privacy drift |
| `scripts/run_suite.py` | Full tier: run every suite and write `report.md` |
| `scripts/serve_local.sh` | Start `wrangler pages dev` with local D1/R2 and wait for health |
| `scripts/lighthouse.sh` | Lighthouse on key pages with pass/fail thresholds |
| `scripts/make_routes.py` | Write `_routes.json` so static files skip Functions |
| `scripts/deploy_batch.sh` | Count changes, gate on the full tier, deploy once |

Config examples live in `templates/`.
